# GearHub Campus 제품과 도메인

## 1. 한 문장 소개

GearHub Campus는 한 대학교의 학과·연구실·동아리가 학교 공용 및 그룹 전용 장비를 대여·반납·도입하고, 관리자가 다음 4주 수요를 예측해 재고를 준비하는 B2B 자산 운영 플랫폼이다.

## 2. 해결할 문제

대학 장비는 학교 공용 창고와 학과·연구실·동아리에 나뉘어 있다. 목록과 승인 방식이 서로 달라 다음 문제가 생긴다.

- 구성원은 자신이 사용할 수 있는 장비와 수량을 한곳에서 보기 어렵다.
- 관리자는 신청, 승인, 실물 반납, 재고 복구를 수기로 연결한다.
- 그룹에 없는 장비가 필요할 때 필요성 검토와 학교 예산 검토가 분리되어 추적이 어렵다.
- 학교는 장비가 부족해진 뒤에야 구매를 검토하고, 다른 그룹의 여유 재고를 먼저 활용하기 어렵다.

제품 가치는 자산 검색 자체보다 대여 생명주기와 도입 의사결정을 하나의 데이터 흐름으로 닫는 데 있다.

## 3. 제품 경계

현재 고객 단위는 한 대학교이며, 그 안에 여러 그룹이 존재한다. 그룹별 서버나 프론트엔드를 별도 배포하지 않고 하나의 애플리케이션에서 groupId로 데이터와 권한 범위를 나눈다.

| 범위 | 결정 |
|---|---|
| 학교 | 1개 |
| 그룹 | 학과, 연구실, 동아리 등 여러 개 |
| 자산 소유 | 학교 공용 또는 특정 그룹 |
| 사용자 소속 | 여러 그룹 참여 가능 |
| 배포 | 단일 Web, 공통 MSA |
| URL | /groups/{groupId}/... |

여러 대학을 각각 고객사로 격리하는 멀티테넌트 SaaS는 후속 범위다.

## 4. 사용자와 권한

| 사용자 | 목표 | 주요 권한 |
|---|---|---|
| 일반 구성원 | 필요한 장비를 빌리고 반납 | 가입 그룹 자산 조회, 대여·반납 요청, 도입 요청 |
| 그룹 관리자 | 그룹 장비와 구성원 운영 | 자산 등록, 대여 승인·반려, 반납 확인, 도입 1차 검토, 입고 |
| 학교 관리자 | 학교 전체 자산·예산 운영 | 모든 그룹 관리, 예산 승인·반려, 수요예측 조회 |

조직 역할은 STUDENT와 INSTRUCTOR, 그룹 역할은 MEMBER와 MANAGER로 구분한다. 학교 관리자 INSTRUCTOR는 전체 그룹에서 관리자 권한을 갖는다.

초대코드는 관리자에게만 노출되며, 구성원은 전달받은 코드로 그룹에 가입한다.

## 5. 핵심 도메인

| 용어 | 정의 |
|---|---|
| 그룹 | 학과·연구실·동아리 등 자산 운영 단위 |
| 멤버십 | 사용자와 그룹의 소속 및 역할 |
| 학교 공용 자산 | ownerGroupId가 없고 조직 범위에 공개된 장비 |
| 그룹 전용 자산 | 특정 ownerGroupId에 속한 장비 |
| 가용 수량 | 지금 승인 가능한 물리 수량 |
| 대여 요청 | 기간과 목적을 포함한 LOAN 요청 |
| 반납 요청 | 구성원이 실물 반납 의사를 표시한 상태 |
| 반납 확인 | 관리자가 실물을 확인하고 재고를 복구하는 행위 |
| 도입 요청 | 그룹에 필요한 미보유 장비의 PURCHASE 요청 |
| 예산 검토 | 학교가 도입 금액을 승인하거나 반려하는 단계 |
| 수요예측 | 그룹 × 카테고리의 다음 4주 예상 대여량 |

## 6. 핵심 업무 흐름

### 6.1 그룹 참여와 자산 조회

1. 사용자가 로그인한다.
2. 가입한 그룹 목록을 확인하거나 초대코드로 참여한다.
3. 그룹 워크스페이스에서 학교 공용 자산과 해당 그룹 자산을 함께 본다.
4. 카테고리, 가용 수량, 픽업 위치, 최대 대여일을 확인한다.

### 6.2 대여와 반납

~~~text
PENDING
  ├─ 승인 → ACTIVE → 반납 요청 → RETURN_REQUESTED → 반납 확인 → RETURNED
  └─ 반려 → REJECTED
~~~

- 요청에는 시작일, 반납 예정일, 사용 목적이 필요하다.
- 승인 시에만 가용 수량을 1 차감한다.
- 재고가 없으면 승인할 수 없다.
- 반납 요청만으로 재고를 복구하지 않는다.
- 관리자가 실물을 확인한 뒤에만 가용 수량을 1 복구한다.
- dueDate가 지났고 ACTIVE 또는 RETURN_REQUESTED이면 연체로 표시한다.

### 6.3 장비 도입

~~~text
PENDING
  ├─ 그룹 승인 → GROUP_APPROVED
  │                 ├─ 예산 승인 → BUDGET_APPROVED → 입고 → RECEIVED
  │                 └─ 예산 반려 → REJECTED
  └─ 그룹 반려 → REJECTED
~~~

- 구성원은 이름, 카테고리, 단가, 수량, 구매 링크, 사유를 입력한다.
- 그룹 관리자는 실제 필요성을 1차 검토한다.
- 학교 관리자는 전체 예산 관점에서 승인 또는 반려한다.
- 예산 결과는 payment.completed 이벤트로 Request에 전달한다.
- 입고 시 PURCHASE_REQUEST 자산이 OWNED와 ACTIVE로 바뀌고 수량이 반영된다.

## 7. 핵심 사용자 스토리

- 구성원으로서 내가 속한 그룹에서 사용할 수 있는 자산만 보고 싶다.
- 구성원으로서 필요한 기간과 목적을 입력해 장비를 신청하고 싶다.
- 구성원으로서 내 요청 상태와 연체 여부를 확인하고 반납을 요청하고 싶다.
- 그룹 관리자로서 신청을 검토하고 재고가 있을 때 승인하고 싶다.
- 그룹 관리자로서 실물을 확인한 뒤 반납을 확정하고 재고를 복구하고 싶다.
- 구성원으로서 그룹에 없는 장비의 도입을 요청하고 싶다.
- 그룹 관리자로서 도입 필요성을 검토해 학교 예산 심사로 넘기고 싶다.
- 학교 관리자로서 예산 요청을 승인·반려하고 그룹별 부족 장비를 미리 보고 싶다.

## 8. AI 기능의 제품 역할

AI는 대여자에게 무엇을 빌릴지 추천하지 않는다. 사용자는 대체로 필요한 장비를 이미 알고 있기 때문이다.

관리자용 수요예측은 다음 질문에 답한다.

1. 각 그룹과 카테고리의 다음 4주 예상 요청량은 얼마인가
2. 평균 대여기간을 고려하면 동시에 몇 대가 필요한가
3. 현재 재고로 충족 가능한가
4. 부족하다면 다른 그룹에서 먼저 몇 대를 이동할 수 있는가
5. 이동으로 해결되지 않으면 어느 도입 요청을 검토해야 하는가

외부 생성형 AI API는 사용하지 않는다. 자체 대여 이력을 scikit-learn으로 분석하고, 최근 4주 평균 기준선과 후보 모델을 같은 시간 구간에서 비교한다.

## 9. MVP 범위

### 포함

- OAuth2 로그인과 사용자 프로필
- 그룹 생성·조회·초대코드 가입·역할
- 학교 공용 및 그룹 전용 자산
- 수량, 픽업 위치, 최대 대여일
- 대여 신청, 승인·반려, 반납 요청·확인, 연체 표시
- 도입 요청, 그룹 검토, 학교 예산 검토, 입고
- Kafka 기반 예산 결과와 대여 생명주기 이벤트
- 78주 시뮬레이션 이력과 LIVE 이벤트 분리
- 모델 비교, 평가 수치, 다음 4주 예측
- 부족 수량과 그룹 간 이동 제안
- Docker Compose 실행과 재현 가능한 데모 시드

### 제외

- 여러 대학 간 데이터 격리와 고객사별 SSO
- 미래 예약 구간의 동시 수량 계산
- 자산 개별 시리얼·손상·수리·분실
- 알림, 실제 발주, 배송, 회계
- 실제 운영 데이터만으로 검증된 모델
- 자동 재학습 스케줄과 드리프트 경보

## 10. 제품 성공 기준

### 실습 인수 기준

- 프론트엔드를 포함한 11개 컨테이너가 실행된다.
- 로그인 후 그룹 목록과 동적 워크스페이스가 열린다.
- 대여 승인 시 재고가 감소하고 반납 확인 시 원복된다.
- 도입 요청이 그룹 승인, 예산 승인, 입고까지 이어진다.
- AI가 다음 4주 수요와 부족·이동 제안을 반환한다.
- 모델 성능이 같은 테스트 구간에서 최근 4주 평균 기준선보다 낫다.
- 운영 데모 데이터와 모델용 시뮬레이션 데이터가 분리된다.

### 운영 전환 후 관찰 지표

- 대여 승인 처리시간
- 연체율과 평균 반납 지연일
- 자산 가동률과 품절 요청률
- 그룹 간 재고 이동으로 해결한 부족 건수
- 도입 요청의 승인 리드타임
- 예측 WAPE와 부족 경보 적중률
- 실제 데이터 비중과 모델 드리프트

## 11. 현재 검증 기준

고정 시드에서 8개 그룹, 120개 자산, 200개 운영 대여, 8개 도입 요청, 10,814개 분석 이벤트를 사용한다. 최종 모델은 Histogram Gradient Boosting이며 WAPE는 기준선 70.3414%에서 55.7159%로 20.79% 개선됐다.

재현 절차와 테스트 결과는 [최종 검증 기록](./10_FINAL_VALIDATION.md)에 정리한다.
