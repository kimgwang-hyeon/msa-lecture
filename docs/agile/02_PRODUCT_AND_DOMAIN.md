# B2B SaaS 서비스 기획과 도메인 매핑

## 1. 한 문장 소개

GearHub는 교육기관·기업이 내부 장비의 보유·대여·구매요청·예산 검토를 한 흐름으로 관리하는 B2B SaaS다.

## 2. 서비스 성격

가이드 2의 B2B/B2BC 관점에 맞춰, GearHub는 일반 소비자용 쇼핑몰이 아니라 조직이 구성원에게 장비를 제공하는 운영 문제를 해결한다. SKALA는 첫 적용·데모 조직이며, 같은 구조를 사내 교육팀·연구소·메이커스페이스·프로젝트 조직에도 적용할 수 있다.

- 구매 고객: 교육기관 운영 조직, 기업 교육·IT·총무·R&D 조직
- 직접 사용자: 교육생·임직원·프로젝트 구성원, 자산 운영자, 예산 승인자
- 조직에 주는 가치: 중복 구매 감소, 자산 활용률 향상, 승인 리드타임 단축, 신청 근거와 상태의 감사 가능성
- 제공 방식: 조직별 내부 포털로 사용하는 SaaS
- 이번 MVP: SKALA 한 조직만 다루는 단일 테넌트 워킹 스켈레톤

### B2B SaaS 제품 경계

| 구분 | 이번 이틀 MVP | 제품화 단계 |
|---|---|---|
| 조직 | SKALA 한 조직 | 여러 고객사·교육기관별 테넌트 분리 |
| 계정 | 기존 OAuth2와 교육생·운영진 역할 | 고객사 SSO, 조직·부서·세분화 권한 |
| 자산 | 보유 장비 목록, 가치, 가용 수량 | 자산 태그, 위치, 감가상각, 점검 이력 |
| 워크플로 | 대여와 신규 구매요청 승인·반려 | 조직별 다단계 결재 정책과 SLA |
| 분석 | 기능 흐름과 데이터 일관성 검증 | 활용률·유휴자산·구매 절감액 대시보드 |
| SaaS 운영 | 로컬 단일 배포 | 테넌트 격리, 감사로그, 요금제, 운영 모니터링 |

멀티테넌시가 없는 현재 코드를 완성형 SaaS라고 과장하지 않는다. 이번 실습은 B2B SaaS의 핵심 업무 흐름을 검증하는 초기 두 Increment다.

## 3. 이해관계자와 Pain Point

| 이해관계자 | 현재 불편 | 영향 | GearHub 가치 |
|---|---|---|---|
| 교육생 | 어떤 장비가 있고 지금 빌릴 수 있는지 알기 어렵다. | 팀별로 운영진에게 반복 문의하고 준비가 늦어진다. | 보유 목록·가용 수량을 직접 확인하고 한 화면에서 신청한다. |
| 교육생 | 새 장비 요청 형식이 일정하지 않다. | 가격·링크·용도가 빠져 재문의가 발생한다. | 상품 링크, 단가, 수량, 사유를 필수 입력한다. |
| 운영진 | 대여와 구매요청이 여러 채널에 흩어진다. | 승인 누락과 재고 오차가 생긴다. | 대여·예산 대기 목록과 상태를 통합 관리한다. |
| 운영진 | 이미 비슷한 장비가 있는데도 구매요청이 들어온다. | 예산이 중복 집행될 수 있다. | 구매 전 같은 카테고리의 대여 가능한 대체재를 확인시킨다. |
| 예산 승인자 | 구매 필요성과 총액을 확인할 자료가 여러 메시지에 흩어진다. | 검토가 지연되고 결정 근거가 남지 않는다. | 상품 링크·수량·총액·사유와 승인 상태를 함께 남긴다. |
| 고객 조직 책임자 | 자산 활용 현황과 요청 처리 수준을 파악하기 어렵다. | 추가 구매와 운영 개선의 근거가 부족하다. | MVP 이후 활용률·승인 리드타임·절감 추정치를 제공한다. |
| 프로젝트 팀 | 승인 결과를 즉시 알기 어렵다. | 시연 일정과 구현 범위를 결정하기 어렵다. | `PENDING/ACTIVE/REJECTED` 상태를 추적한다. |

## 4. 문제 가설과 검증 질문

### 문제 가설

조직의 보유 현황과 구매요청 근거를 같은 흐름에서 관리하면 반복 문의와 승인 리드타임, 중복 구매 가능성을 줄일 수 있다.

### 이틀 실습에서 확인할 질문

1. 교육생이 운영진에게 별도 문의하지 않고 대여 가능한 장비를 찾을 수 있는가?
2. 대여 신청 후 운영진 승인과 재고 차감이 일관되게 처리되는가?
3. 구매요청 전에 보유 대체재를 반드시 확인하게 할 수 있는가?
4. 예산 승인·반려 결과가 비동기 이벤트로 신청 상태에 반영되는가?

실제 운영 효과를 증명하려면 장기간 사용자 데이터가 필요하므로, 이틀 동안에는 기능 흐름과 데이터 일관성을 검증한다.

### 제품화 이후 측정 지표

- 대여 가능 장비를 찾기까지 걸린 시간
- 구매요청 전 대체재 확인률과 요청 철회율
- 요청 생성부터 승인·반려까지의 리드타임
- 전체 자산 대비 대여 중인 자산 비율
- 대체재 사용으로 줄인 것으로 추정되는 구매 금액

## 5. 템플릿 도메인 매핑

| 온라인 교육 템플릿 | GearHub 개념 | 설명 |
|---|---|---|
| 수강생 | 교육생 | 교보재를 대여하거나 구매를 요청하는 사용자 |
| 강사 | 운영진 | 교보재를 등록하고 신청을 검토하는 사용자 |
| 강의 | 교보재·구매요청 상품 | 기존 `Course` 모델을 자산 카탈로그로 재사용 |
| 강의 등록 | 보유 교보재 등록 | 자산가치와 전체 수량 입력 |
| 수강신청 | 대여·구매 신청 | `requestType`으로 두 신청을 구분 |
| 결제 | 예산 검토 | 돈을 결제하지 않고 승인·반려만 수행 |
| 결제 완료 | 예산 승인 | `COMPLETED` 이벤트가 Request를 `ACTIVE`로 전환 |
| 결제 실패 | 예산 반려 | `FAILED` 이벤트가 Request를 `REJECTED`로 전환 |
| 강의 추천 | 보유 대체재 추천 | 신규 구매 전에 같은 카테고리의 재고를 제시 |

## 6. 서비스 경계

| 서비스 | 책임 | 변경 이유 |
|---|---|---|
| Member Service | 교육생·운영진 계정과 역할 | User 템플릿을 그대로 활용 |
| Asset Service | 보유 교보재, 자산가치, 수량, 구매요청 상품 | Course를 재고가 있는 자산으로 확장 |
| Request Service | 대여·구매 신청과 상태 | Enrollment를 두 종류의 요청으로 확장 |
| Budget Service | 예상 총액과 예산 승인·반려 | Payment의 상태 머신을 예산 검토로 재해석 |
| Alternative Service | 구매 전 보유 대체재 조회 | Recommend의 규칙 기반 조회를 도메인에 맞게 변경 |

## 7. 핵심 사용자 스토리

### 교육생

- 교육생으로서 프로젝트에 사용할 수 있는 교보재와 가용 수량을 보고 싶다. 그래야 운영진에게 먼저 물어보지 않고 준비할 수 있다.
- 교육생으로서 사용 목적을 적어 대여를 신청하고 싶다. 그래야 운영진이 필요성을 판단할 수 있다.
- 교육생으로서 보유하지 않은 장비의 상품 링크와 예상 금액을 제출하고 싶다. 그래야 신규 구매 검토를 받을 수 있다.
- 교육생으로서 신청 상태와 반려 사유를 확인하고 싶다. 그래야 프로젝트 계획을 조정할 수 있다.

### 운영진

- 운영진으로서 대여 대기 목록과 현재 재고를 함께 보고 싶다. 그래야 재고를 초과해 승인하지 않을 수 있다.
- 운영진으로서 예상 총액과 상품 링크를 보고 예산을 승인·반려하고 싶다. 그래야 실제 결제 없이도 의사결정을 기록할 수 있다.

## 8. AI·추천 역할

### 현재 Sprint 2에서 구현한 수준

- 같은 카테고리의 `OWNED` 교보재 중 가용 수량이 1개 이상인 항목을 최대 5개 제시한다.
- 규칙이 단순하고 설명 가능하므로 이틀짜리 MVP에서 결과를 검증하기 쉽다.
- 현재 구현은 머신러닝 모델이 아니라 규칙 기반 추천 기준선이다.

### 이후 AI 실험 가설 (`FUTURE`)

- 구매요청의 상품명·설명·사유와 보유 교보재 설명을 임베딩으로 비교한다.
- 카테고리가 달라도 실제 용도가 유사한 대체재를 찾는다.
- 운영진에게 추천 근거와 유사도를 제공한다.
- 통계 담당이 추천 적중률, 대체재 클릭률, 추천 후 구매요청 철회율을 평가한다.

AI를 구현한 것처럼 과장하지 않고, 현재 규칙 기반 결과를 기준선으로 삼아 다음 스프린트의 모델 실험 가능성을 보여주는 것이 목표다.

## 9. MVP 범위

### 포함

- OAuth2 로그인과 역할 구분
- 보유 교보재 목록·상세·카테고리·가용 재고
- 운영진 교보재 등록
- 대여 신청과 승인·반려
- 승인 시 재고 차감
- 신규 구매요청과 서버 측 총액 계산
- 구매 전 보유 대체재 확인
- 예산 승인·반려와 Kafka 상태 연동
- 내 신청과 운영진 승인 화면

### 제외

- 실제 PG 결제, 발주와 배송
- 반납·연장·분실 처리
- 날짜별 예약
- 이메일·메신저 알림
- 모델 학습과 벡터 검색
- 운영 분석 대시보드
- 멀티테넌시, 고객사별 데이터 격리와 요금제
- 기업 SSO, 조직·부서별 권한과 감사로그

## 10. 실습 성공 기준

| 기준 | 목표 |
|---|---|
| 대여 흐름 | 신청부터 승인·재고 차감까지 오류 없이 완료 |
| 재고 안전성 | 가용 수량 0 미만 방지 |
| 구매요청 완전성 | 상품명·단가·수량·URL·사유·대체재 확인 필수 |
| 금액 일관성 | 클라이언트 값이 아니라 서버가 `단가 × 수량` 계산 |
| 상태 일관성 | Budget 결과와 Request 결과가 Kafka를 통해 일치 |
| 설명 가능성 | 추천 이유가 동일 카테고리·가용 재고라는 규칙으로 설명 가능 |

## 11. B2B SaaS 확장 백로그

| ID | 제품화 기능 | 우선순위 | 이유 |
|---|---|---|---|
| SAAS-01 | 조직(tenant) 생성과 모든 업무 데이터의 조직별 격리 | Must | 여러 고객이 안전하게 쓰기 위한 선행 조건 |
| SAAS-02 | 고객사 SSO와 조직·부서·권한 관리 | Must | 기업 도입과 운영자 권한 통제에 필요 |
| SAAS-03 | 승인자·단계·한도액을 설정하는 조직별 워크플로 | Should | 기관마다 다른 구매 정책을 수용 |
| SAAS-04 | 자산 활용률·승인 리드타임·구매 절감 추정 대시보드 | Should | 구매 담당자에게 도입 효과를 설명 |
| SAAS-05 | 변경 이력과 승인 감사로그 | Should | 책임 추적과 내부 감사 지원 |
| SAAS-06 | 요금제·계약·고객 지원 관리 | Could | 상용 SaaS 운영 단계에서 필요 |
