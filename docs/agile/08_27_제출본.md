맞아요. 이전 정리는 백엔드·AI 흐름에 치우쳐서 우리가 작성했던 로고, 버튼, 로그인·회원가입 라우팅, 카드, 아이콘, 체크리스트 같은 프론트 개선 내용이 빠졌습니다. 아래처럼 제품 기능과 프론트 개선을 함께 보여줘야 합니다.

# 1. 이해관계자와 Pain Point

### 핵심 메시지

> 장비 운영 흐름이 분리되어 있을 뿐 아니라, 화면의 디자인과 조작 방식도 통일되지 않아 사용자가 현재 상태와 다음 행동을 이해하기 어렵다.

| 이해관계자 | 기능적 Pain Point | 프론트엔드 Pain Point |
|---|---|---|
| 일반 구성원 | 사용 가능한 장비와 승인 상태를 확인하기 어려움 | 버튼·아이콘이 페이지마다 다르고, 로그인에서 회원가입 이동이 백엔드 화면으로 연결됨 |
| 그룹 관리자 | 승인, 반납 확인, 재고 복구가 분리됨 | 반납 검수 체크박스와 관리 버튼이 직관적이지 않고 상태 구분이 약함 |
| 학교 관리자 | 부족 발생 후에야 구매를 검토함 | 관리자 박스와 버튼 색상이 원색적이고, AI 결과의 정보 계층이 일관되지 않음 |

### 해결해야 할 핵심 문제

- 대여·반납·도입·예측 흐름을 하나로 연결
- 화면마다 다른 버튼, 카드, 아이콘 디자인 통일
- 로그인과 회원가입을 프론트엔드 라우팅으로 연결
- 상태 변화를 사용자가 명확하게 인식하도록 개선
- 키보드, 반응형, 모션 감소 설정 등 접근성 보완

# 2. GearHub 솔루션과 AI·Frontend 역할

## 서비스 핵심 흐름

```text
로그인·회원가입
→ 그룹 참여
→ 장비 조회
→ 대여 신청·승인
→ 반납 요청·검수
→ 장비 도입·예산 승인
→ 4주 수요예측
```

## AI의 역할

- 78주 대여 이력으로 그룹·카테고리별 다음 4주 수요예측
- 필요 수량과 부족 수량 계산
- 다른 그룹의 여유 재고 이동 제안
- 부족이 남으면 신규 장비 도입 검토
- 기준선과 모델 오차를 함께 표시해 판단 근거 제공

## Frontend의 역할

- 노드·엣지 기반의 `#4276A6` GearHub 로고로 브랜드 통일
- 버튼, 카드, 입력창, 아이콘을 공통 디자인 시스템으로 구성
- 로그인과 회원가입을 `/login`, `/register`로 분리
- 대여·반납·예산 상태 변화를 화면에서 명확하게 표현
- AI 예측값을 차트, 위험도, 부족 수량, 이동 제안으로 시각화
- 반응형, 키보드 접근성, `prefers-reduced-motion` 지원

### 핵심 메시지

> AI가 미래 부족을 계산한다면, Frontend는 그 결과를 사용자가 이해하고 실제 행동으로 옮길 수 있도록 전달한다.

## 전체 Sprint 구성

| 구분 | Sprint 1, 핵심 가치·MVP | Sprint 2, 확장·완성도 |
|---|---|---|
| 제품 기능 | 그룹 장비 대여·승인·반납 | 도입·예산·입고·AI 예측 |
| 서비스 | Member, Asset, Request | Budget, Kafka, Analytics |
| Frontend 목표 | 디자인 기준과 인증 진입 흐름 확립 | 전체 기능 화면에 디자인 확장 |
| 주요 화면 | 홈, 로그인, 회원가입, 그룹, 장비, 대여 | 반납 검수, 관리자, 도입·예산, AI 대시보드 |
| 검증 | 대여 승인 재고 -1, 반납 확인 재고 +1 | 예산 이벤트, 입고 전환, AI 결과와 관리자 행동 |

- 로그인과 회원가입 화면의 디자인 통일
- 학교·캠퍼스 형태의 프로필 아이콘 적용

## Sprint 2 Frontend Backlog

- 유색 회색 카드를 반투명 공통 카드로 개선
- 반복되는 카드 레이아웃에 크기와 강조 변화 적용
- 내 대여, 그룹, 장비, 관리자 아이콘 통일
- 반납 검수 체크박스를 선택형 행 UI로 개선
- 관리자 페이지의 원색적인 하늘색 박스 개선
- 대여·반납·예산 상태 배지 통일
- AI 예측 화면의 정보 계층과 시각화 개선
- 페이지 진입과 카드 hover 애니메이션 적용
- 모바일·태블릿·데스크톱 반응형 검증
- `prefers-reduced-motion`과 키보드 접근성 검증

## Sprint를 나눈 이유

- Sprint 1에서 공통 디자인 기준을 먼저 확정해야 전체 화면의 재작업을 줄일 수 있다.
- 로그인·회원가입과 대여·반납은 사용자가 처음부터 끝까지 이용하는 핵심 흐름이다.
- Sprint 2의 관리자·AI 화면은 Sprint 1의 데이터와 디자인 시스템에 의존한다.

## Sprint 1 리뷰 → Sprint 2 반영

```text
Sprint 1 리뷰
```

# 4. Frontend를 포함한 MSA 아키텍처

```text
사용자
  ↓
Vue Frontend
  ├─ Vue Router
  │   ├─ /login
  │   ├─ /register
  │   ├─ /groups/:id/assets
  │   ├─ /groups/:id/loans
  │   ├─ /groups/:id/admin
  │   └─ /groups/:id/analytics
  │
  ├─ 공통 UI
  │   ├─ 디자인 토큰
  │   ├─ Button·Input·Card
  │   ├─ SVG Logo·Icon
  │   └─ Animation·Accessibility
  │
  └─ API Client
        ↓ Bearer Token
API Gateway ─── Auth Server
  │
  ├─ Member Service
  ├─ Asset Service
  ├─ Request Service
  ├─ Budget Service
  └─ Demand Analytics

Request ──REST── Member·Asset·Budget
Budget ── payment.completed ── Kafka ── Request
Request ── rental.lifecycle ── Kafka ── Analytics
Analytics ── 현재 재고 조회 ── Asset

각 서비스는 Eureka에 등록·탐색
```

### Frontend 연결 원칙

- 브라우저는 모든 API를 Gateway를 통해 호출
- 인증 토큰은 `Authorization: Bearer` 헤더로 전달
- `/register`는 프론트엔드 화면이지만 기존 `POST /api/users/register` 재사용
- 화면 상태와 API 상태 계약을 동일하게 표현
- 백엔드 API 주소, 요청 필드, 응답 구조는 변경하지 않음

# 5. 화면별 API 연결

| Frontend 화면·행동 | API | 화면 변화 |
|---|---|---|
| 회원가입 제출 | `POST /api/users/register` | 성공 메시지 후 `/login` 이동 |
| 그룹 참여 | `POST /api/users/groups/join` | 참여 그룹 목록 갱신 |
| 장비 목록 | `GET /api/courses?groupId={id}` | 공용·그룹 장비 카드 표시 |
| 대여 신청 | `POST /api/enrollments` | `PENDING` 상태 표시 |
| 관리자 대여 승인 | `POST /api/enrollments/{id}/approve` | `ACTIVE`, 재고 -1 |
| 반납 요청 | `POST /api/enrollments/{id}/return-request` | `RETURN_REQUESTED` |
| 반납 검수 완료 | `POST /api/enrollments/{id}/return-confirm` | `RETURNED`, 재고 +1 |
| 도입 요청 | `POST /api/enrollments/acquisitions` | 구매 요청 상태 표시 |
| 예산 승인 | `POST /api/payments/{id}/approve` | `BUDGET_APPROVED` 반영 |
| 입고 확인 | `POST /api/enrollments/{id}/receive` | 장비가 `OWNED·ACTIVE`로 전환 |
| AI 성능 조회 | `GET /api/recommend/analytics/evaluation` | 기준선·모델 성능 카드 |
| AI 예측 조회 | `GET /api/recommend/analytics/forecast?groupId={id}` | 수요·부족·이동 제안 표시 |

### 회원가입 프론트엔드 연결

```text
/login에서 회원가입 클릭
→ Vue Router /register
→ RegisterView.vue
→ authApi.register()
→ POST /api/users/register
→ 성공 메시지
→ Vue Router /login
```

이 흐름에서는 `localhost:8080`의 백엔드 HTML 회원가입 화면으로 이동하지 않는다.

# 6. Frontend 동작 화면 스냅샷

## 화면 1. 브랜드와 인증 흐름

캡처 내용:

- `#4276A6` 노드·엣지 GearHub 로고
- 개선된 시작하기 버튼
- 로그인 오른쪽 상단 X 버튼
- `/login → /register` 이동
- 로그인과 회원가입의 통일된 입력창·버튼 디자인

캡션:

> 로그인과 회원가입을 Vue Router 기반의 독립 화면으로 구성하고 동일한 브랜드 디자인을 적용했다.

## 화면 2. 그룹·장비 화면

캡처 내용:

- 학교·캠퍼스 프로필 아이콘
- 그룹 참여 버튼
- 반투명 장비 카드
- 통일된 장비 아이콘
- 카드 hover 또는 진입 애니메이션

캡션:

> 버튼, 카드, 아이콘을 공통 디자인 시스템으로 통일하고 그룹별 장비 접근 범위를 시각적으로 구분했다.

## 화면 3. 대여 승인 전·후

| 승인 전 | 승인 후 |
|---|---|
| 상태 `PENDING` | 상태 `ACTIVE` |
| 가용 재고 `N` | 가용 재고 `N-1` |

캡션:

> 관리자가 승인하면 상태 배지가 변경되고 동일한 장비의 가용 재고가 1 감소한다.

## 화면 4. 반납 검수 전·후

| 반납 요청 | 검수 완료 |
|---|---|
| `RETURN_REQUESTED` | `RETURNED` |
| 재고 변화 없음 | 재고 +1 |
| 선택형 검수 항목 미완료 | 검수 항목 완료 표시 |

캡션:

> 기본 체크박스를 접근 가능한 선택형 검수 UI로 개선하고, 실물 확인 후에만 재고가 복구되도록 했다.

## 화면 5. 관리자 도입·예산 화면

캡처 내용:

- 저채도 반투명 관리자 정보 박스
- 도입 요청 상태
- 그룹 승인과 예산 승인
- 입고 후 `OWNED·ACTIVE` 전환
- 공통 버튼과 상태 배지

캡션:

> 관리자 페이지도 홈페이지와 동일한 디자인 언어를 적용하고 도입·예산·입고 상태를 명확하게 표현했다.

## 화면 6. AI 대시보드

캡처 내용:

- 기준선 WAPE `70.34%`
- 모델 WAPE `55.72%`
- 개선율 `20.79%`
- 다음 4주 예측
- 필요 수량과 부족 수량
- 위험도 및 그룹 간 이동 제안

캡션:

> AI 예측 결과를 카드와 차트로 시각화하고, 관리자가 재고 이동 또는 신규 도입을 결정할 수 있도록 구성했다.

이렇게 수정하면 발표에서 백엔드·MSA·AI뿐 아니라 “프론트엔드가 사용자 문제를 어떻게 해결했고 Sprint별로 어떻게 발전했는지”도 명확하게 드러납니다.
