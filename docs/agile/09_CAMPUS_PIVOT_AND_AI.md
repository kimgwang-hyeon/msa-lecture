# GearHub Campus 제품 전환과 AI 설계

## 1. 최종 제품 결정

GearHub Campus는 한 대학교 안의 여러 학과·연구실·동아리가 장비를 공유하는 B2B 자산 운영 시스템이다.

초기 아이디어는 조직 하나의 교보재 대여·구매요청이었다. 대화를 통해 실제 사용 상황을 다시 검토하면서 다음 문제를 더 중요한 것으로 정의했다.

- 학교 공용 장비와 그룹 자체 장비가 서로 다른 곳에서 관리된다.
- 구성원은 어느 그룹의 장비를 볼 수 있는지 알기 어렵다.
- 대여 승인만 있고 반납 확인과 재고 복구가 없으면 운영 흐름이 끝나지 않는다.
- 없는 장비는 단순 구매 버튼이 아니라 그룹 필요성 검토와 학교 예산 검토를 거쳐야 한다.
- 대여자가 무엇을 빌릴지는 이미 알고 있는 경우가 많아 개인 추천 AI의 가치가 낮다.
- 관리자는 다음 학기·행사 기간에 어느 장비가 부족할지 판단할 데이터가 부족하다.

따라서 최종 목표를 다음처럼 잡았다.

> 학교와 소속 그룹의 자산을 하나의 흐름으로 대여·반납·도입하고, 관리자가 다음 4주 재고를 데이터로 준비하게 한다.

## 2. 사용자와 권한

| 사용자 | 주요 목표 | 구현된 권한 |
|---|---|---|
| 일반 구성원 | 자산 조회, 대여·반납, 미보유 장비 도입 요청 | 가입 그룹의 공용·그룹 자산 조회 및 요청 |
| 그룹 관리자 | 그룹 구성원과 자산 운영 | 대여 승인·반려, 반납 확인, 도입 1차 검토, 입고 |
| 학교 관리자 | 학교 전체 자산·예산 운영 | 모든 그룹 관리, 예산 승인·반려, AI 수요예측 |

조직 역할은 기존 템플릿의 `STUDENT / INSTRUCTOR`를 유지했고, 그룹 안의 역할은 `MEMBER / MANAGER`로 분리했다. 학교 관리자(`INSTRUCTOR`)는 모든 그룹에서 관리자처럼 동작한다.

초대코드는 그룹 관리자 응답에만 노출된다. 일반 구성원은 전달받은 코드로 참여할 수 있지만 API 응답으로 코드를 다시 조회할 수 없다.

## 3. 그룹 라우팅 결정

그룹마다 애플리케이션이나 Docker 컨테이너를 따로 띄우지 않는다. 하나의 배포 안에서 URL과 데이터 범위만 동적으로 분리한다.

```text
/groups
/groups/{groupId}
/groups/{groupId}/assets
/groups/{groupId}/loans
/groups/{groupId}/acquisitions/new
/groups/{groupId}/admin
/groups/{groupId}/analytics
```

이 선택의 이유는 다음과 같다.

- 그룹이 추가될 때 새 서버를 배포할 필요가 없다.
- 공통 기능 수정이 모든 그룹에 동시에 적용된다.
- `groupId`와 멤버십 검증으로 권한 범위를 일관되게 적용할 수 있다.
- 학교 전체 공용 자산과 그룹 전용 자산을 한 화면에서 조합하기 쉽다.

현재 MVP는 한 학교 안의 멀티그룹이다. 여러 학교를 고객사로 받는 멀티테넌트 SaaS가 되려면 이후 모든 주요 테이블에 `organization_id`를 추가하고 고객사별 SSO·정책·감사로그를 분리해야 한다.

## 4. 최종 도메인 흐름

### 4.1 대여와 반납

```text
PENDING
  ├─ 그룹 관리자 승인 → ACTIVE → 구성원 반납 요청 → RETURN_REQUESTED
  │                                              └─ 관리자 확인 → RETURNED
  └─ 그룹 관리자 반려 → REJECTED
```

- 신청 시 요청 기간과 사용 사유를 저장한다.
- 승인 시 Asset Service가 가용 수량을 1 감소시킨다.
- 동시 승인으로 재고가 음수가 되지 않도록 자산 버전과 트랜잭션 검증을 사용한다.
- 반납 요청만으로는 재고를 올리지 않는다.
- 관리자가 실물을 확인해 반납 확정했을 때만 가용 수량을 1 복구한다.
- `dueDate < 오늘`이고 아직 반납되지 않은 요청은 연체로 표시한다.

### 4.2 미보유 장비 도입

```text
PENDING
  ├─ 그룹 승인 → GROUP_APPROVED
  │                 ├─ 학교 예산 승인(Kafka) → BUDGET_APPROVED → 입고 → RECEIVED
  │                 └─ 학교 예산 반려(Kafka) → REJECTED
  └─ 그룹 반려 → REJECTED
```

입고 확정 시 기존 구매요청 자산이 `OWNED / ACTIVE`로 전환되고 승인된 수량만큼 `totalQuantity`와 `availableQuantity`가 설정된다. 따라서 요청 문서가 실제 대여 가능한 자산으로 이어진다.

## 5. 기존 MSA 템플릿과의 매핑

| 기존 물리 구조 | 최종 업무 의미 |
|---|---|
| User Service / `users` | 학교 사용자 |
| 새 `campus_groups`, `group_memberships` | 그룹과 소속·역할 |
| Course Service / `courses` | 자산 및 도입 대상 |
| Enrollment Service / `enrollments` | 대여·반납·도입 요청 |
| Payment Service / `payments` | 실제 결제가 아닌 학교 예산 검토 |
| Recommend Service | 기존 대체재 API + 관리자용 Demand Analytics |

포트, Java 패키지, 주요 API prefix, 물리 테이블을 가능한 범위에서 유지했다. 이것은 실습 코드 재사용이라는 제약 안에서 도메인 의미를 바꾼 ACL(Anti-Corruption Layer) 성격의 결정이다.

## 6. AI 문제 정의

### 채택하지 않은 안

- 대여자 개인 추천: 사용자는 대개 필요한 장비를 이미 알고 있어 의사결정 가치가 작다.
- 외부 생성형 AI API 호출: 데이터 분석 결과가 아니라 문장 생성에 그칠 수 있어 실습 평가 근거가 약하다.
- 연체자 위험 점수: 개인을 평가하는 기능은 데이터 편향·설명 가능성·운영 책임이 크다.

### 채택한 안

> 관리자용 `그룹 × 자산 카테고리` 주간 대여 수요 예측

관리자가 실제로 결정할 수 있는 행동과 연결했다.

1. 다음 4주 예상 요청량을 본다.
2. 평균 대여기간을 이용해 동시에 필요한 수량을 환산한다.
3. 그룹 전용 재고와 배분된 학교 공용 재고를 비교한다.
4. 부족하면 먼저 여유가 있는 다른 그룹의 이동 가능 수량을 제안한다.
5. 이동으로 해결되지 않을 때 도입 검토 근거로 사용한다.

## 7. 학습 데이터와 모델

### 데이터 단위

- 집계 단위: 주
- 분석 축: `groupId × category`
- 목표값: 해당 주의 대여 요청 건수
- 기간: 78주(약 18개월)
- 최종 시뮬레이션 이벤트: 10,814건

### 특징값

- 1·2·4주 전 요청량(lag)
- 최근 4주 이동평균과 표준편차
- 주차의 사인·코사인 순환 특징
- 그룹과 자산 카테고리

### 시간순 평가

랜덤 분할을 사용하지 않았다. 미래 데이터가 과거 학습에 섞이는 누수를 막기 위해 앞 구간을 학습, 다음 구간을 검증, 마지막 구간을 테스트로 사용했다.

비교 대상은 다음과 같다.

- 기준선: 최근 4주 이동평균
- Poisson Regressor
- Random Forest Regressor
- Histogram Gradient Boosting Regressor

검증 WAPE가 가장 낮은 모델을 선택하고, 보지 않은 테스트 구간에서 기준선과 최종 성능을 비교한다.

### 최종 고정 시드 결과

| 항목 | 값 |
|---|---:|
| 선택 모델 | Histogram Gradient Boosting |
| 기준선 MAE | 1.4717 |
| 모델 MAE | 1.1657 |
| 기준선 WAPE | 70.3414% |
| 모델 WAPE | 55.7159% |
| 기준선 대비 개선 | 20.79% |
| 학습 행 수 | 3,248 |
| 테스트 행 수 | 672 |

정확도가 완벽하다고 주장하지 않는다. 중요한 점은 단순 기준선보다 나은지 같은 테스트 구간에서 측정하고, 관리자 화면에 모델명·기준선·오차를 함께 공개했다는 것이다.

## 8. 운영 데이터와 분석 데이터 분리

시연 화면에 18개월치 요청 10,814건을 그대로 넣으면 사용성이 무너진다. 따라서 다음처럼 분리했다.

| 데이터 | 목적 | 저장 방식 |
|---|---|---|
| 운영 데모 대여 200건 | 내 요청·승인·반납 화면 시연 | `enrollments` |
| 분석 시뮬레이션 10,814건 | 모델 학습과 비교 | `analytics_loan_events.source='SIMULATION'` |
| 실제 신규 이벤트 | 운영 중 학습 이력 축적 | Kafka → `source='LIVE'` |

시드 재실행 시 `SIMULATION`만 교체하므로 실제 `LIVE` 이벤트는 보존된다.

## 9. Agile 관점의 변경과 배운 점

이번 전환은 처음 계획을 그대로 지키는 것보다 사용자 가치에 맞춰 Product Backlog를 다시 정제한 사례다.

- “그룹마다 서버를 하나씩 만든다” 대신 동적 워크스페이스로 운영 비용을 줄였다.
- “대여 승인”을 완료로 보지 않고 반납 확인과 재고 복구까지 수직 흐름을 닫았다.
- “AI를 넣는다”를 목표로 두지 않고 관리자 재고 결정이라는 액션에서 역으로 문제를 정의했다.
- 모델 성능만 보여주지 않고 기준선, 시간순 분리, 부족 수량, 이동 대안까지 연결했다.
- 실습 템플릿을 전면 재작성하지 않고 서비스 책임과 상태를 확장해 제한된 시간 안에 워킹 소프트웨어를 만들었다.

발표에서는 코드량보다 이 제품 판단을 먼저 설명하는 편이 좋다. 핵심 메시지는 “주제를 바꾼 것”이 아니라 “사용 맥락을 검토해 가치가 낮은 추천을 버리고, 운영자가 행동할 수 있는 예측으로 범위를 재정의한 것”이다.

## 10. MVP 이후 백로그

- 학교별 완전한 멀티테넌시와 고객사 SSO
- 날짜 구간별 수량 예약 충돌 계산
- 손상·분실·수리 상태와 자산 개별 시리얼 추적
- 알림과 승인 SLA
- 학사 일정·행사 일정 외생 변수
- 실제 데이터가 충분해졌을 때 시뮬레이션 비중 축소
- 모델 드리프트 감지와 정기 재학습
- 내부 API 인증, 감사로그, OAuth2 PKCE/BFF 적용
